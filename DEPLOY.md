# Deploying Fleet Watch Pro to Render

This repo ships a [`render.yaml`](./render.yaml) Blueprint that provisions the
**entire stack** — Postgres, Redis, the FastAPI backend, and the static SPA —
from one file. Migrations run automatically on every release.

## 1. Push to GitHub

```bash
git remote add origin git@github.com:<you>/fleet-watch-pro.git
git push -u origin main
```

## 2. Create the Blueprint

Render dashboard → **New → Blueprint** → select this repo. Render reads
`render.yaml` and creates four resources:

| Resource           | What it is                                  |
| ------------------ | ------------------------------------------- |
| `fleetwatch-db`    | Postgres 16 (`DATABASE_URL` auto-injected)  |
| `fleetwatch-redis` | Key Value store (`REDIS_URL` auto-injected) |
| `fleetwatch-api`   | FastAPI backend (Docker)                    |
| `fleetwatch-web`   | Static SPA (Vite build)                     |

`JWT_SECRET_KEY` is generated by Render. `DATABASE_URL` / `REDIS_URL` are wired
automatically. The backend refuses to start with an insecure secret or empty
CORS in prod, so these guards are real.

## 3. Fill the values that need live URLs

The first deploy creates the service URLs; set these once they exist, then
redeploy:

| Service          | Env var        | Value                                          |
| ---------------- | -------------- | ---------------------------------------------- |
| `fleetwatch-api` | `CORS_ORIGINS` | `https://<fleetwatch-web URL>`                 |
| `fleetwatch-api` | `GPS_API_KEYS` | comma-separated device keys you issue          |
| `fleetwatch-web` | `VITE_API_URL` | `https://<fleetwatch-api URL>`                 |
| `fleetwatch-web` | `VITE_WS_URL`  | `wss://<fleetwatch-api URL>`                   |

Then edit the **Content-Security-Policy** header in `render.yaml` (line marked
`CHANGE-ME`): replace `https://api.example.com` / `wss://api.example.com` with
your real `fleetwatch-api` origin, commit, and push. Without this the browser
blocks API/WebSocket calls.

## 4. Seed the first admin

In the `fleetwatch-api` service shell (Render → Shell):

```bash
SEED_ADMIN_EMAIL=admin@yourcompany.uz \
SEED_ADMIN_PASSWORD='<strong-password>' \
python seed.py
```

Registration via `POST /api/auth/register` also creates an org + admin if you
prefer self-serve onboarding.

## 5. Mobile app

In `mobile/eas.json`, replace the `EXPO_PUBLIC_API_URL` placeholders
(`https://api.fleetwatch.uz`) with your real `fleetwatch-api` URL per profile,
then build with EAS. The URL **must be HTTPS** for a shipped build.

---

## Known scaling caveat

The live-map WebSocket fan-out is **per-process**. One `fleetwatch-api`
instance is correct out of the box. Before scaling the backend to >1 instance,
add Redis pub/sub so location updates fan out across replicas (tracked as a
follow-up). Everything else (rate limiting, refresh tokens, scheduler lock)
already shares state through Redis.

## Alternative: Railway / VPS

Both Dockerfiles bind the platform `$PORT` and the backend migrates on start, so
they run as-is on Railway (deploy each Dockerfile as a service, add Postgres +
Redis plugins) or a Docker host. For the frontend image, pass the API origin at
runtime so the CSP allows it:

```bash
docker run -e API_ORIGIN=https://api.your-host -e WS_ORIGIN=wss://api.your-host ...
```

and build with `--build-arg VITE_API_URL=https://api.your-host` so Vite bakes
the right API base into the bundle.
